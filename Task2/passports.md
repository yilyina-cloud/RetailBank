# Паспорта инициатив: данные, качество и эксперимент

- для инициатив №1, №18 и №5.

Все размеры выборок, сроки, ставки и пороги ниже — проектные допущения. Их нужно согласовать с владельцами процессов и DS-командой. Проверки ещё не проводились; качество моделей пока неизвестно.

## 1. Приоритизация проверки операций

### Постановка

- Цель: повысить пользу проверок при текущей мощности финмониторинга.
- Объект: операция с учётом истории клиента и связанных платежей.
- Вход: табличные данные операций, история и сигналы правил.
- Операция модели: поиск аномалий.
- Выход модели: оценка нетипичности, не вероятность схемы.
- Выход для бизнеса: очередь ручной проверки с учётом обязательных сроков и приоритетов.
- Решение по операции принимает сотрудник. Модель не блокирует и не одобряет платежи.

На первом этапе меняем порядок уже помеченных операций. Отдельная контрольная выборка включает и операции вне отбора правилами. Расширение модельного отбора на весь поток — отдельное решение после пилота.

### Качество

| Что оцениваем | Как проверяем |
|---|---|
| Baseline | Текущий порядок: правила и внешние сигналы, затем приоритет крупных сумм |
| Польза модели | Доля случаев, требующих углублённого разбора по экспертному гайдлайну, среди первых K операций |
| Подтверждённые схемы | Считаем отдельно, после появления результатов; не заменяем их эскалациями |
| Рабочая точка | Первые K операций в пределах доступного времени сотрудников |
| Ограничения | Не ухудшаются сроки обязательных проверок, очередь по возрасту, число лишних приостановок и жалоб |
| Цена ошибок | Ложный приоритет занимает время сотрудника; низкий приоритет важной операции задерживает выявление. Денежная цена пропуска неизвестна |

K не равно автоматически 10 тыс. операций в месяц: из общей мощности нужно вычесть обязательные проверки и время на контрольную выборку.

Предлагаемый критерий пилота: не менее 20% относительного роста доли полезных проверок против baseline при одинаковом бюджете человеко-часов. Например, с 5% до 6%, а не до 25%. Это целевой минимум для обсуждения, не прогноз качества.

Исторические 4% эскалаций не считаем готовым baseline этой метрики: сначала нужно применить единый критерий разметки.

Recall по всем реальным схемам пока неизвестен. Контрольная выборка даст оценку по экспертным меткам с учётом вероятностей отбора и неопределённости.

### Готовность данных

| Проверка | Состояние и действие |
|---|---|
| Источник и владелец | История операций — владелец банковских данных; результаты проверок — руководитель финмониторинга. Конкретных ответственных назначить |
| Источник ответа | Экспертная разметка, исход расследования и формальное подтверждение — отдельные поля |
| Объём | Есть история за несколько лет и 20–25 млн операций в месяц. Подтверждённых схем — единицы; для обучения классификатора их недостаточно |
| Разметка | Согласовать гайдлайн. Метки для оценки очереди: «нужен углублённый разбор», «не нужен», «недостаточно сведений» |
| Согласованность | 20% выборки проверяют два эксперта. Предлагаемый порог Cohen’s kappa — 0,7; ниже него сначала уточняем гайдлайн |
| Смещение отбора | Ранее проверяли операции, выбранные правилами и сигналами. Непроверенные не равны чистым |
| Репрезентативность | Проверить сегменты бизнеса, суммы, каналы, новых клиентов и разные периоды |
| Качество | Проверить пропуски, дубли, связи клиента и контрагента, даты и задержки обновления |
| Утечка | В признаки не включать исход расследования и сведения, появившиеся после момента оценки |
| Холодный старт | Клиенты без истории идут по текущим правилам; качество для них измеряется отдельно |
| Право обработки | Комплаенс, DPO и юристы подтверждают цель, состав данных, доступ и сроки хранения |

**Вердикт: разрыв с планом закрытия.** Обучение классификатора откладываем. Для проверки поиска аномалий сначала нужны экспертный набор, проверка доступности признаков и согласование обработки данных.

### Проверочный набор

Начальная оценка объёма — 2 000 операций:

- 1 000 из потока помеченных операций;
- 1 000 из вероятностной выборки всего потока, включая непомеченные.

Выборку стратифицируем по сегментам и суммам, сохраняем вероятность включения. Объём увеличиваем, если целевых случаев слишком мало для устойчивого сравнения.

Модель обучаем без целевых меток на более ранней истории. Размеченные примеры разделяем на validation и более поздний test по 1 000 операций, сохраняя оба источника отбора. Связанные эпизоды не разделяем между наборами.

Подготовку признаков настраиваем только на train. По validation выбираем кандидата и рабочую точку; test не используем для настройки.

### Эксперимент

**Гипотеза:** оценка нетипичности помогает выбрать более полезные проверки, чем приоритет только по сумме.

**Альтернативы:** модель выделяет обычные особенности отдельных сегментов; признаки устарели; эксперты неодинаково понимают критерии.

Порядок:

1. Проверить признаки и согласованность разметки.
2. Сравнить baseline и два кандидата на одной validation-выборке.
3. Проверить результат по сегментам, затем на независимом test.
4. Провести теневой прогон: модель предлагает очередь, рабочий процесс пока не меняется.

Эксперты по возможности не видят, каким способом отобран случай.

Оценка подготовки: 2–4 недели. При 12 минутах на операцию разбор 2 000 случаев займёт 400 часов; повторная проверка 20% — ещё 80 часов. При условной ставке 1 000 ₽/час — 480 тыс. ₽ только на разметку, без споров и работы DS.

Если ресурс выделяется из текущей команды, уменьшается её доступная мощность. Это нужно согласовать до начала.

**Результат:**
- Есть устойчивый выигрыш и ограничения соблюдены — переходим к ограниченному пилоту.
- Выигрыша нет — разбираем ошибки и проверяем другую гипотезу.
- Данных мало — расширяем выборку; успех не объявляем.

## 2. Извлечение финансовых показателей

### Постановка

- Цель: сократить поиск и перенос данных при разборе кредитной заявки.
- Объект: показатель, его значение, период, валюта и единица измерения.
- Вход: текст, таблицы, сканы и фотографии отчётности и выписок.
- Операция: извлечение полей; при необходимости — OCR.
- Выход модели: поля со ссылками на страницу и фрагмент источника; отсутствующее значение — null.
- Выход для бизнеса: показатели для проверки андеррайтером и список проблем.
- Модель не оценивает подлинность документа и не принимает кредитное решение.

### Качество

| Что оцениваем | Предложение для пилота |
|---|---|
| Baseline | Ручное извлечение и проверка тех же полей |
| Точность полей | Не менее 98% полных совпадений: значение + период + валюта + единица |
| Выдуманные значения | Ноль обнаруженных критичных значений без подтверждения источником на приёмочном наборе |
| Полнота | Не менее 95% обязательных полей, которые действительно есть и читаются в документе |
| Бизнес-эффект | Сокращение медианного времени извлечения и проверки минимум на 20% |
| Ограничения | После проверки сотрудником ошибок не больше, чем при ручном процессе |

Пороги предложены для пилота: цена неверной суммы выше цены ручного разбора пустого поля. Их утверждает руководитель андеррайтинга.

Ноль ошибок в тесте не означает отсутствие риска в проде. В пилоте сотрудник подтверждает все критичные поля.

### Готовность данных

| Проверка | Состояние и действие |
|---|---|
| Источник и владелец | Кредитные пакеты; владелец — подразделение андеррайтинга |
| Источник ответа | Поля, сверенные специалистами с оригиналами |
| Объём | Общий объём документов и количество примеров по форматам неизвестны |
| Разметка | Указать значение, период, единицу и место в источнике; спорные поля проверяет второй эксперт |
| Смещение | Не ограничиваться одобренными заявками и чистыми PDF |
| Репрезентативность | Включить сканы, фотографии, таблицы, длинные документы, разные формы и единицы |
| Качество | Нечитаемость отличать от отсутствия поля; разные форматы сами по себе не означают плохие данные |
| Утечка | Не разделять документы одной заявки между validation и test |
| Доступность | Извлекать данные только из документов, доступных к моменту анализа заявки |
| Право обработки | DPO, ИБ и юристы согласуют использование документов, контур, логи и хранение |

**Вердикт: разрыв с планом закрытия.** Документы есть, но проверенный набор и условия использования не подтверждены.

План: андеррайтинг отбирает документы и размечает поля, DS проверяет покрытие форматов, ИБ и юристы согласуют обработку.

### Наборы и эксперимент

- 20 документов — диагностика: пропуски, противоречия, плохие сканы, длинные таблицы, разные единицы.
- 300 других документов — начальный проверочный набор: 150 validation и 150 test.
- Не менее 30 документов каждого ключевого формата в test. Если форматов много, набор увеличиваем.
- Редкие опасные случаи проверяем дополнительно; их результаты не смешиваем с оценкой обычного потока без весов.

Сравниваем:
1. Парсер/OCR → текстовая модель → проверки.
2. Исходный документ → мультимодальная модель → проверки.

Для сравнения текстовых моделей используем одинаковый распознанный вход. Затем сравниваем оба пути целиком.

**Гипотезы:** ошибки возникают в OCR, в извлечении полей или в проверках после модели. На части проблемных документов вручную исправляем OCR и повторяем прогон — это помогает отделить причины.

Оценка подготовки: 2–3 недели. При 15 минутах на документ и повторной проверке 20% разметка 300 документов займёт около 90 часов. При условной ставке 1 000 ₽/час — 90 тыс. ₽. Прогоны и интеграция считаются отдельно.

Если качество проходит пороги, но время не сокращается, пересматриваем интерфейс и ручную проверку. Если остаются выдуманные критичные значения, расширение пилота останавливаем.

## 3. Маршрутизация обращений

### Постановка

- Цель: быстрее направлять обращения в нужный отдел.
- Объект: обращение свободным текстом.
- Вход: текст, канал и продукт.
- Операция: классификация по темам.
- Выход модели: тема и оценка уверенности.
- Выход для бизнеса: отдел назначения или ручная маршрутизация.
- Правила связывают тему с отделом; неоднозначные случаи разбирает диспетчер.

Допущение из Task1: надёжной темы, выбранной клиентом, нет. Если она есть и достаточна, используем правила и заменяем инициативу для дальнейшей ML-проработки.

### Качество

| Что оцениваем | Предложение для пилота |
|---|---|
| Baseline | Текущая маршрутизация и простые правила по ключевым словам |
| Сравнение моделей | Macro-F1 по темам и ошибки каждого отдела |
| Рабочая точка | Порог уверенности, выбранный на validation |
| Автоматический маршрут | Не менее 95% верных назначений при покрытии не менее 50% обращений |
| Бизнес-эффект | Медианное время до нужного отдела уменьшается минимум на 20% |
| Ограничения | Не растёт доля повторных переводов; срочные обращения не задерживаются |

95% и 50% — предложенный баланс качества и доли автоматизации. Если порог достигается только на нескольких процентах обращений, пользы для процесса может не быть.

### Готовность данных

| Проверка | Состояние и действие |
|---|---|
| Источник и владелец | Система обращений; владелец — руководитель клиентской поддержки |
| Источник ответа | Проверенный конечный маршрут и экспертная разметка темы |
| Объём | История и число примеров по отделам пока не подтверждены |
| Разметка | Согласовать темы, обращения с несколькими вопросами и категорию «нужен диспетчер» |
| Смещение | Исторические переводы могли быть ошибочными или зависеть от загрузки отдела |
| Репрезентативность | Разные каналы, продукты, короткие тексты, опечатки, редкие и новые темы |
| Качество | Убрать дубли; цепочку переписки хранить как связанный объект |
| Утечка | Не использовать ответы операторов и сведения о маршруте как входные признаки |
| Право обработки | Проверить состав ПДн, банковской тайны, права доступа и сроки хранения |

**Вердикт: разрыв с планом закрытия.** Сначала подтвердить источник текстов и корректных маршрутов.

### Наборы и эксперимент

Предварительный объём — 3 000 размеченных обращений:
- 1 800 train;
- 600 validation;
- 600 test из более позднего периода.

Одна цепочка и её дубли остаются в одном наборе. В test нужно хотя бы 50 примеров каждой темы, допущенной к автоматизации. При нехватке примеров расширяем набор или оставляем тему диспетчеру.

Диагностический набор: 20 обращений с опечатками, несколькими темами, неизвестными продуктами и недостатком информации.

**Гипотеза:** модель лучше простых правил определяет тему свободного текста.

**Альтернативы:** выбранной клиентом темы уже достаточно; список отделов неоднозначен; проблема в исторической разметке.

Сначала проверяем эти альтернативы, затем сравниваем модели. Если правила достигают тех же показателей дешевле, выбираем правила.

Оценка подготовки: 2–3 недели. При 2 минутах на обращение и повторной проверке 20% потребуется около 120 часов. При условной ставке 800 ₽/час — 96 тыс. ₽ без DS и интеграции.

Если качество и покрытие проходят пороги — ограниченный пилот. Если не проходят — ручная маршрутизация и разбор причин, без снижения требований ради запуска.

## Общие правила проверки

- Размеры наборов — стартовая оценка, а не гарантия статистической надёжности.
- Вместе с метриками показываем число примеров, ошибки по сегментам и доверительные интервалы.
- Пороги и кандидатов выбираем на validation.
- Test открываем для итоговой оценки. После многократного подбора по нему он перестаёт быть независимым.
- Версионируем данные, разметку, подготовку признаков, модель и настройки.
- Недостаточно сведений — отдельный исход, а не отрицательная метка.
- Юридические условия подтверждают юристы, DPO и комплаенс; эти паспорта не заменяют их заключение.
