# ADR-002. Извлечение финансовых показателей

Дата: 2026-11-16  
Статус: предложено, до сравнительного прогона

## Контекст

Документы кредитной заявки приходят в разных форматах. Разбор пакета занимает около 1,5 часа, но доля времени на извлечение показателей неизвестна.

Нужно получать проверяемые поля с источниками, а не свободный пересказ документа.

## Решение по данным

Собрать набор документов с полями, проверенными андеррайтерами. Включить разные форматы, пустые поля, противоречия и нечитаемые участки.

Документы одной заявки не разделять между validation и test. План проверки — в [паспорте](passports.md).

## Выходной контракт

Для каждого показателя:
- название;
- значение или null;
- период, валюта и единица;
- документ, страница и фрагмент источника;
- статус: найдено / отсутствует / нечитаемо / противоречие.

Схема ответа проверяет форму, но не достоверность. Код проверяет типы, единицы, периоды и арифметические связи. Сотрудник подтверждает критичные поля.

## Кандидаты и сравнение

| Вариант | Что проверяем |
|---|---|
| Обычный парсер и правила | Baseline для структурированных таблиц и устойчивых форм |
| Парсер/OCR + небольшая управляемая текстовая модель | Извлечение полей из нормализованного документа |
| Парсер/OCR + open-weight текстовая модель | То же извлечение при самостоятельном размещении |
| Мультимодальная модель | Работа со сложными таблицами и страницами без отдельного OCR |

Это предварительный список классов решений. Конкретные модели и версии фиксируем перед прогоном после проверки лицензий, доступности в разрешённом контуре и поддержки русского языка.

Предпочтительный путь для проверки: парсер/OCR → текстовая модель → проверки. Для PDF с корректным текстовым слоем OCR не нужен.

Сохраняем страницы, таблицы, координаты и версию распознавания. Плоского текста недостаточно для привязки значения к строке и колонке.

Диагностика — 20 документов; дальнейшая проверка — 300 документов по паспорту. Сравниваем качество полей, ручные исправления, задержку и стоимость полного пути.

Кандидат, который выдумывает критичные поля, не проходит приёмку. Если исправленный вручную OCR устраняет ошибки, сначала исправляем распознавание, а не меняем LLM.

## Размещение

- Публичный API для реальных документов пока не допускаем: условия обработки не согласованы.
- Для синтетической диагностики API возможен, но такая проверка не подтверждает качество на реальных документах.
- Пилот на реальных данных: предварительно выделенный контур провайдера, если условия подтвердят ИБ и юристы.
- Прод: сравнить выделенный контур и self-hosting в согласованном облаке по качеству, нагрузке и TCO.
- On-premises остаётся вариантом при наличии ресурсов и команды; закупку GPU до проверки пользы не планируем.

Предварительно выделенный контур выбран ради сокращения работ по эксплуатации. Наличие подходящего предложения — допущение, которое требуется проверить.

До передачи документов согласовать регион обработки и резервных копий, хранение и удаление, доступ поддержки, логи и запрет обучения на запросах. Private endpoint сам по себе не доказывает изоляцию вычислений.

## Ответственность и риски

Провайдер отвечает за модельный сервис по договору. Банк — за данные, права доступа, интеграцию, проверки результата и решение по заявке.

Присланный клиентом документ считается недоверенным содержимым: инструкции внутри него не должны менять задачу модели. Доступа к платёжным и кредитным действиям у модели нет.

Основные риски: неверный период или масштаб суммы, выдуманные поля, утечка данных, смена версии и дорогая ручная перепроверка.

Стоимость включает распознавание, вход и выход модели, повторные запросы, инфраструктуру и работу андеррайтера.

## Допущения, выход и пересмотр

Пока неизвестны объём документов, длина, доля сканов и готовность внутренней команды.

Сохраняем собственную схему полей, исходники, представление OCR и тестовые наборы. Доступ к провайдеру — через заменяемый адаптер.

Модель и версию фиксируем перед тестами. При обновлении запускаем диагностику и регрессионный набор; изменение принимаем после проверки, с возможностью отката.

Пересмотр нужен при:
- ошибках в критичных полях;
- появлении новых форматов;
- отсутствии экономии времени;
- изменении лицензии или условий обработки;
- росте стоимости документа более чем вдвое против согласованной оценки.

Последний порог — предлагаемое условие пересмотра, а не известная стоимость.
